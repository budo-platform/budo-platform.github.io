Native C projects #

Native C applications are ahead-of-time projects. Budo owns the process entry point, so application sources implement budo_get_application() and must not define main().

Native code is trusted and unsandboxed. Compiling or packaging an untrusted project is equivalent to compiling arbitrary native code.

Create a project #

Generate the core canvas starter:

Terminal
budo init my-native-app --language c

The optional advanced template demonstrates shaders, textures, buffers, and a mesh:

Terminal
budo init my-native-gpu-app --language c --template gpu

Both templates write main.c, budo-native.json, .gitignore, a README, and VS Code settings for the generated compilation database. Native initialization refuses to add C files over an existing managed main.js, main.ts, main.lua, main.wat, or main.wasm entrypoint.

Project detection #

A native project input is resolved in this order:

  1. A directory containing budo-native.json.
  2. A directory containing main.c, mapped to a one-source default project.
  3. A single .c file, mapped to a one-source project rooted at its parent directory.

Managed budo run entrypoints are unchanged. Native projects are inputs to budo compile, not to budo run, and watch mode does not apply.

Manifest #

budo-native.json is a strict JSON object. Unknown and duplicate fields are rejected. The supported schema is:

| Field | Required | Meaning | |---|---|---| | schema_version | Yes | Must be 1. | | sources | Yes | Non-empty array of project-relative .c files. | | name | No | Application/output name; defaults to the project directory name. | | include_directories | No | Project-relative directory paths. | | assets | No | Project-relative files or directories copied beside the executable while preserving their paths. File-backed native shader and image APIs resolve only through these staged project assets. | | definitions | No | Compile definitions such as FEATURE=1; shell/CMake syntax is not accepted. | | modules | No | Selected Budo modules. core currently includes lifecycle, input, canvas, and native GPU shader/texture/buffer/mesh services. | | c_standard | No | 11 (default), 17, or 23. Extensions are disabled. | | sdk_version | No | Requested Budo SDK version; defaults to the running Budo version. |

Every declared path must be relative, exist, stay within the canonical project root, and contain no . or .. segment. Symlinks that resolve outside the project are rejected. Arbitrary CMake, Make, shell, compiler, linker, and build-hook fields are intentionally unsupported.

Declare every shader or image passed to a file-backed native graphics API in assets. Desktop compilation copies it beside the executable and Android packaging places it in the existing application asset pipeline while preserving the same relative path.

Compile command #

Build a native project from a local checkout with:

budo compile <FILE|DIRECTORY>
budo compile <FILE|DIRECTORY> --build-dir <DIRECTORY>
budo compile <FILE|DIRECTORY> --sdk <UNPACKED-SDK>
budo compile <FILE|DIRECTORY> --offline
budo compile <FILE|DIRECTORY> --run
budo compile <FILE|DIRECTORY> --debug
budo compile <FILE|DIRECTORY> --release
budo compile <FILE|DIRECTORY> --debug --sanitize address,undefined

The default generated/build directory is <project>/.budo/native. --run starts the new executable only after compilation succeeds. --watch is explicitly rejected because native changes require recompilation and process restart.

Without --sdk, the command first uses a complete matching checkout SDK when one is present. Installed CLIs otherwise resolve the current version and target tuple from release metadata whose SHA-256 was pinned independently when the CLI was configured. A release must configure both BUDO_NATIVE_SDK_RELEASE_METADATA_URL and BUDO_NATIVE_SDK_RELEASE_METADATA_SHA256; fetching metadata beside an archive without that independent pin is deliberately not authoritative.

--sdk selects a trusted local relocatable SDK and BUDO_NATIVE_SDK_DIR is the lower-priority trusted local equivalent. Trusting the selection does not skip integrity checking: every listed inner-manifest member, size, and SHA-256 must match, no unlisted file may exist, and links/special files are rejected. Relocatable and downloaded SDK builds resolve CC, CXX, and CMake on the host instead of inheriting compiler paths from the SDK producer. The SDK CMake package then enforces its compiler/target constraints.

Automatic downloads verify the pinned release record, archive size and digest, safe archive member set, exact inner manifest, target tuple, version, inner manifest digest, and SDK input identity. Extraction accepts only bounded USTAR regular files/directories under one root; absolute/traversing paths, duplicate members, links, special members, oversized files, and member/total-size bombs fail closed. Installation is locked and atomic. Test and private distribution systems may override the metadata URL and its mandatory independent SHA-256 via BUDO_NATIVE_SDK_RELEASE_METADATA_URL and BUDO_NATIVE_SDK_RELEASE_METADATA_SHA256; file:// is supported for deterministic local tests.

--offline (or BUDO_NATIVE_SDK_OFFLINE=1) forbids network access and requires the pinned metadata and verified archive to be cached. Corrupt installed SDKs are recovered from a valid cached archive. SDKs live under a separate native-sdks cache, not the native executable-result cache:

budo cache sdk inspect [--json]
budo cache sdk clean --all
budo cache native inspect [--json]
budo cache native clean --all

Each clean command affects only its named namespace. CMake diagnostics are printed directly, and successful builds report executable, compilation database, and provenance paths. Provenance includes the verified inner-manifest, release metadata, archive, and SDK input digests.

Native source is trusted and unsandboxed. The command prints this warning before invoking the compiler.

The default build is RelWithDebInfo: optimized application code with symbols. --debug selects an unoptimized debug build and --release selects an optimized release build. On Clang and GCC, --sanitize address, --sanitize undefined, or both as address,undefined instruments application sources and links the matching runtime. Prebuilt Budo, Skia, and SDL libraries are not instrumented. Sanitizers are rejected with --release and with unsupported compiler families rather than being silently ignored.

For Android, package the same source with Budo Pro:

Terminal
budo android-apk my-native-app
budo android-aab my-native-app --release

See Native C debugging for debugger and sanitizer workflows. Cache diagnostics are available through budo cache native inspect and budo cache sdk inspect; build identity and invalidation details are also recorded in budo-native-build.json.

Generated build #

The normalized model generates a private CMake project. It enables compile_commands.json, compiles only declared sources with declared includes and definitions, stages declared assets, and links the exported budo::native_launcher target. The generated project also writes budo-native-project.json for inspection and diagnostics.

The local checkout export uses the matching BudoNativeTargets.cmake, SDL2 package discovery, and local Skia library. An unpacked SDK instead supplies a relocatable BudoNative CMake package containing the public headers, Budo host archives, Skia closure, SDL2 runtime, licenses, target/compiler constraints, and application configuration helper. Generated builds consume either form through the same project model.

The generated directory contains:

  • CMakeLists.txt and budo-native-project.json — inspectable generated input and normalized model.
  • build/compile_commands.json — editor compilation database.
  • build/bin/<application> — executable and staged assets.
  • budo-native-build.json — SDK/build identity, platform, architecture, compiler, CMake generator, dependency inputs, and output path.

Reusing the directory gives CMake normal dependency-based incremental compilation. Completed executables also use the content-addressed native build cache. SDK identity is based on its manifest/tree contents rather than its unpack location, so relocating an unchanged SDK does not invalidate the cache.

Producing a desktop SDK #

make native-sdk builds the host closure as RelWithDebInfo, installs the NativeSDK component under build/native-sdk/stage, validates and writes its complete SHA-256 file manifest, and creates a deterministic .tar.gz (.zip on Windows) plus an outer release record. Set SOURCE_DATE_EPOCH and BUDO_NATIVE_SDK_BUILD_ID in release jobs. Artifact tuples are macos-arm64-apple, macos-x86_64-apple, linux-x86_64-gnu, and windows-x86_64-msvc; only tuples exercised by clean CI should be published.

The macOS package targets AppleClang and a macOS 11 deployment baseline, Linux targets x86-64 with a glibc 2.31 baseline and platform OpenGL/FreeType/Fontconfig, and Windows targets MSVC v143 with the dynamic CRT. SDL2 is staged beside the application by the package helper; macOS load commands and Linux runtime search paths are made relocatable. Native SDK archives retain optimized debug symbols.
